# LiteEA: Lite Enterprise Architecture (Architecture-as-Code)

A lightweight, Git-based enterprise architecture methodology that combines ArchiMate 3.2 semantics with modern development workflows. **Multi-tenant** organization structure for managing architecture across multiple companies.

## 📁 Project Structure

```
LiteEA/
├── organizations/                # Each organization has its own directory
│   ├── acme_corp/               # Example: ACME Corporation
│   │   ├── elements/            # Architecture elements by layer
│   │   │   ├── 01_motivation/
│   │   │   ├── 02_business/
│   │   │   ├── 03_application/
│   │   │   └── 04_technology/
│   │   ├── relations/           # Relationships (atomic separation)
│   │   ├── .templates/          # Templates for creating elements
│   │   ├── .validators/         # Validation scripts
│   │   ├── views/               # Diagram configurations
│   │   ├── 0.archive/           # Archive directory (not deletion)
│   │   ├── README.md            # Organization-specific guide
│   │   ├── GETTING_STARTED.md   # Quick start for this org
│   │   └── CONVENTIONS.md       # Naming standards
│   │
│   └── your_company/            # Add your organization here
│       └── (same structure as acme_corp)
│
├── method/                       # Methodology documentation
│   └── LiteEA Методология...md  # Full methodology (Russian)
├── .github_workflows_example.yaml # CI/CD pipeline example
└── README.md                     # This file
```

## 🚀 Quick Start

### 1. Add Your Organization

```bash
# Copy example organization as template
cp -r organizations/acme_corp organizations/your_company

# Or start from scratch
mkdir -p organizations/your_company/{elements/{01_motivation,02_business,03_application,04_technology},relations,.templates,.validators,views,0.archive}
```

### 2. Create Your First Element

```bash
cd organizations/your_company

# Copy template
cp .templates/elements/03_application_template.yaml \
   elements/03_application/MY_SERVICE.yaml

# Edit with your details
editor elements/03_application/MY_SERVICE.yaml
```

### 3. Validate

```bash
python3 .validators/lint.py
```

### 4. Commit to Git

```bash
git add organizations/your_company/
git commit -m "docs(arch): add new service for your_company"
```

## 🏢 Organization Structure (Per Company)

Each organization folder contains:

### `elements/` - Architecture Elements
Organized by ArchiMate layers:
- **01_motivation/** - Goals, principles, constraints, drivers
- **02_business/** - Roles, actors, processes, functions
- **03_application/** - Services, components, interfaces
- **04_technology/** - Infrastructure, nodes, artifacts

### `relations/` - Element Relationships
All relationships stored separately (atomic principle):
- Source and target IDs must reference valid elements
- Each relation in its own file for clean Git diffs

### `.templates/` - Starting Templates
- **elements/** - Templates by layer for quick element creation
- **relations/** - Relation template with all fields
- **bpmn/** - BPMN process template for workflows
- **EXAMPLES.md** - Real-world examples (e-commerce, etc.)

### `.validators/` - Validation Tools
- **lint.py** - Python linter checking:
  - YAML syntax validity
  - Atomicity (no relations in element files)
  - Referential integrity (all IDs exist)
  - Policy compliance (active elements have owners)

### `views/` - Diagram Configurations
- Specifications for generating visualizations:
  - PlantUML diagrams
  - Mermaid flowcharts
  - SVG exports
- Automatically regenerated by CI/CD

### `0.archive/` - Historical Elements
Instead of deleting elements, move them here to preserve history.

### Organization Documentation
- **README.md** - Overview of the organization's architecture
- **GETTING_STARTED.md** - Tutorial for team members
- **CONVENTIONS.md** - Naming standards and best practices

## ✅ Validation Rules (All Organizations)

Every organization uses the same validation rules:

### Syntax
- All YAML files must be valid

### Atomicity
- **Never** put relations inside element files
- Relations must be separate files in `relations/`

### Referential Integrity
- All `source` and `target` IDs must point to existing elements
- Duplicate IDs not allowed within an organization

### Policies
- **Active/Production status** requires assigned owner
- Critical elements require approval before changes
- All metadata must be complete

### Semantic Compliance
- Relations must follow ArchiMate layer rules
- Element types must match ArchiMate definitions

## 🛠️ Managing Multiple Organizations

### List all organizations
```bash
ls -la organizations/
```

### Validate all organizations
```bash
for org in organizations/*/; do
  echo "Validating $(basename $org)..."
  cd "$org"
  python3 .validators/lint.py
  cd ../..
done
```

## 📊 Scaling Considerations

### For 1-2 Organizations
- Use single repository structure (current)
- Share CI/CD pipeline for all validations

### For 5-10 Organizations
- Keep in single repo with org-specific branches
- Use organization-specific CI/CD triggers
- Implement organization-scoped validation

### For 10+ Organizations
- Consider separate repositories per organization
- Use Git submodules to reference shared `.templates/` and `method/`
- Implement centralized validation service
