Create New Organization:
  → ./create_organization.sh my_company

Create First Element:
  → cd organizations/my_company
  → cp .templates/elements/03_application_template.yaml \
       elements/03_application/MY_SERVICE.yaml
  → vim elements/03_application/MY_SERVICE.yaml
  → python3 .validators/lint.py

Create Relationship:
  → cp .templates/relations/relation_template.yaml \
       relations/SERVICE_TO_DB.yaml
  → vim relations/SERVICE_TO_DB.yaml
  → python3 .validators/lint.py

Commit to Git:
  → git add organizations/my_company/
  → git commit -m "docs(arch): add service element [APP-XXX-001]"

📋 KEY PRINCIPLES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✓ ATOMICITY
  └─ Relations are NEVER inside element files
     All relations go in separate files in relations/ directory

✓ ARCHITECTURE-AS-CODE
  └─ Everything stored in Git as text files (YAML)
     Diagramming and reports are auto-generated artifacts

✓ SINGLE SOURCE OF TRUTH
  └─ Elements describe only themselves
     Relations are separate documents
     Git diffs show exactly what changed

✓ ArchiMate 3.2 COMPLIANCE
  └─ Elements follow ArchiMate layer model:
     Motivation → Business → Application → Technology

✓ MULTI-TENANT
  └─ Each organization has complete isolated structure
     Can share templates and validators across organizations

⚙️ VALIDATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Each organization includes a linter that validates:

  ✓ YAML Syntax
    All files must be valid YAML

  ✓ Atomicity
    No relations section inside element files

  ✓ Referential Integrity
    All source/target IDs in relations must exist

  ✓ Policy Compliance
    Active elements must have assigned owner

Run validator:
  cd organizations/[your_org]
  python3 .validators/lint.py
