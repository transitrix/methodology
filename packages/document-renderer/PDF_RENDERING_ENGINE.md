# HTML-to-PDF rendering engine

**Status:** Specification  
**Decided:** 2026-09-02  
**Applies to:** document-view PDF rendering with paged-media CSS support

## Overview

Document views (printed or exported as PDF) require **paged-media CSS support** for:
- Landscape pages (page size and orientation changes)
- Running headers and footers
- Named pages with distinct styling per section
- Break rules (page-break-before, -after, -inside)

This document specifies the HTML-to-PDF rendering engine and its integration contract.

## Engine choice: Option 2 (Reference renderer)

**Standing shape:** Caller-supplied engine (Option 3)  
**Reference implementation:** Vivliostyle (Option 2)  
**Reference rationale:** Complete paged-media CSS support; open-source and accessible to all adopters; Node.js native integration

The **reference renderer** is the engine used in our canonical workflows and test fixtures. Adopters may supply their own engine **if and only if it satisfies the same paged-media feature matrix** (below).

### Why Vivliostyle as reference

1. **Paged-media CSS:** Complete support for all required features (named pages, page-size, break rules, running elements, string-set counters)
2. **Accessibility:** Free and open-source (AGPL-3.0/MPL-2.0 dual license); no licensing barrier for adopters or public methodology
3. **Integration:** Native Node.js package; runs natively in CI/CD pipelines without external tools
4. **Maintenance:** Actively maintained (August 2026 release); recent fixes for named-page edge cases improve production readiness

### Adopter's choice

An adopter may substitute a different engine **if it supports the paged-media feature matrix.** When it does not:
- The adopter documents which features are unsupported
- Workflow documentation must note these limitations
- Unsupported features fail audibly (error or explicit warning), never silently

## Paged-media CSS feature matrix

| Feature | Vivliostyle | Adopter engine | Status |
|---|---|---|---|
| `@page` rule | ✓ | ? | Required |
| `size: A4; margin: ...` | ✓ | ? | Required |
| `@page :first` / `:left` / `:right` | ✓ | ? | Required |
| `page-size: landscape` / `portrait` | ✓ | ? | Required |
| `page-break-before: always` | ✓ | ? | Required |
| `page-break-inside: avoid` | ✓ | ? | Required |
| Named pages (`page: <name>`) | ✓ | ? | Required |
| Running elements (`running()`) | ✓ | ? | Required for footers |
| String set (`string-set`) | ✓ | ? | Required for page counters |
| Content counters (`counter()`) | ✓ | ? | Required |
| `@supports` queries | ✓ | ? | Recommended |
| Embedded fonts (@font-face) | ✓ | ? | Recommended |

**Required features:** All marked "Required" must be supported.  
**Recommended features:** Nice-to-have; absence should be noted in adopter docs, not hidden.

## Integration contract

### Interface

Rendering happens at the boundary between:
- **Input:** HTML + CSS (generated by `document-view-engine`)
- **Output:** PDF bytes (read and verified by caller)

### Caller's responsibility

The caller (Studio, an adopter's pipeline, Methodology's own tools):
1. Generates valid HTML + CSS from a recipe
2. Supplies it to the rendering engine
3. Validates output (file size, page count, etc.)
4. Handles rendering failures

### Engine's responsibility

The rendering engine (Vivliostyle, WeasyPrint, Chromium, …):
1. Accepts HTML + CSS on stdin or as a file
2. Applies paged-media CSS rules
3. Outputs a valid PDF on stdout
4. Reports errors on stderr

### How Methodology calls it

**Current state:** Unimplemented. Rendering engine is a caller-supplied parameter.

**Expected usage pattern** (when implemented):

```javascript
// Pseudocode — not yet built
const html = generateViewHTML(recipe, model)
const css = generateViewStylesheet(recipe)
const pdf = await renderHTMLToPDF(html + css, {
  engine: 'vivliostyle',  // or 'weasyprint', 'chromium', … (if they satisfy feature matrix)
  pageSize: 'A4',
  margins: { top: 20, bottom: 20, left: 15, right: 15 }
})
```

**Responsibility split:**
- Methodology/caller: HTML + CSS generation, validation
- Engine: CSS interpretation, PDF output
- Studio: Chooses engine, handles integration

## Conformance testing

Test fixtures for paged-media features:
- Named pages (section boundaries)
- Landscape pages (wide diagrams)
- Running footers (document metadata)
- Page breaks (sections don't split mid-heading)

Each test has:
1. Input: HTML + CSS exercising a paged-media feature
2. Expected output: PDF with the correct structure
3. Verification: Page count, page orientation, footer content

Conformance = engine produces the expected PDF on all fixtures.

## Limitations and open questions

**Raster images:** Embedded images (PNG, JPG) are deferred. Methodology specifies the contract; Studio implements the integration.

**Fonts:** Embedded or subsetting @font-face rules for non-base14 fonts is deferred. Most workflows use system fonts only.

**Accessibility:** PDF/A compliance, tagged PDFs, and screen-reader support are out of scope for this task. Studio's choice of engine may support these; Methodology documents the contract only.

## CSS generation and Vivliostyle integration

**Status:** Implemented in this package

Methodology provides a dependency-free module for generating paged-media CSS with running footers, landscape pages, and typography rules. The module lives in `packages/document-renderer/src/render-vivliostyle.mjs`.

### What the module provides

- `generatePagedMediaCss(metadata)` — generates CSS with @page rules, running footer, landscape page detection, and base typography
- `wrapHtmlForPrintRendering(html, metadata)` — wraps HTML content with embedded CSS for rendering

### Paged-media CSS features implemented

| Feature | Status | Notes |
|---------|--------|-------|
| Running footer | ✓ Done | Shows issuer, date, identity, commit, page number |
| Page margins and size | ✓ Done | A4 (595 × 842 pt), 20mm margins |
| Page counters | ✓ Done | `counter(page)` and `counter(pages)` available |
| Landscape pages | ✓ Done | `@page landscape` rule; A4 rotated (842 × 595 pt) |
| Wide view detection | ✓ Done | Automatically detects views where width > height and applies landscape page |
| Typography rules | ✓ Done | Headings, paragraphs, lists, code, blockquotes, tables |
| Page break avoidance | ✓ Done | Headings and figures use `page-break-after/inside: avoid` |
| First page footer suppression | ✓ Done | Title page has no footer |

### How to integrate with Vivliostyle

For adopters or tools that need to render HTML to PDF:

```javascript
import { wrapHtmlForPrintRendering } from '@transitrix/document-renderer/src/render-vivliostyle.mjs';

// Your HTML content (with id attributes on diagrams)
const html = `
  <h1>Title</h1>
  <p>Content...</p>
  <div id="diagram-architecture">
    <svg><!-- wide diagram, 1200 x 600 --></svg>
  </div>
`;

// Metadata for the footer and view dimensions
const metadata = {
  issuer: 'Acme Corp',
  issued_at: '2026-09-02T15:30:00Z',
  document_identity: 'PRODUCT-MRD-1.0',
  repository_commit: 'a1b2c3d4',
  views: [
    { id: 'diagram-architecture', width: 1200, height: 600 }, // wide: uses landscape page
  ],
};

// Get HTML with embedded CSS
const htmlWithCss = wrapHtmlForPrintRendering(html, metadata);

// Pass to Vivliostyle (or your chosen engine) for PDF rendering
// E.g., via documents-cli or a headless browser
// The wide diagram automatically renders on a landscape page.
```

**Wide view handling:** Pass a `views` array in metadata. For each view with `width > height`, the CSS generator creates a rule that applies landscape page layout automatically. The HTML element must have an `id` matching the view's `id`.

The HTML output is ready for any CSS Paged Media Module Level 3 compliant renderer.
