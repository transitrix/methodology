# LiteEA: Методология управления архитектурой предприятия (Architecture-as-Code)

Методология **LiteEA** (Lite Enterprise Architecture) — это облегченный подход к проектированию и управлению корпоративной архитектурой, построенный на принципах **Architecture-as-Code (AaC)**. Она объединяет семантическую строгость стандарта **ArchiMate 3.2** с гибкостью текстовых форматов и инструментов разработки, обеспечивая высокую скорость моделирования, прозрачность решений и бесшовную интеграцию с процессами CI/CD.

------

## 1. Основные принципы (Core Principles)

Методология базируется на четырех «столпах», оптимизирующих работу архитекторов и технических лидеров:

- **Единый источник истины (Single Source of Truth):** Архитектурная модель хранится в Git в виде структурированных текстовых файлов (YAML). Диаграммы, отчеты и документация являются производными артефактами, генерируемыми автоматически.
- **Читаемость и прозрачность (Scannability):** Каждый элемент модели должен быть понятен человеку при просмотре в терминале или текстовом редакторе без специального ПО.
- **Автоматизация и валидация (Automation):** Целостность связей, соответствие стандартам и проверка архитектурных ограничений (fitness functions) выполняются скриптами автоматически.
- **Атомарность и декомпозиция (Atomic Elements):** Полное разделение описания объектов и их связей. Запрещено хранить объект и его связи в одном файле для обеспечения чистоты Git-диффов и независимой валидации графа.

------

## 2. Структура репозитория

Архитектурный репозиторий LiteEA имеет иерархическую структуру, соответствующую слоям ArchiMate:

- **`elements/`**: База архитектурных примитивов:
  - `01_motivation/`: Цели, принципы, ограничения, драйверы.
  - `02_business/`: Роли, процессы, акторы, функции.
  - `03_application/`: Компоненты, сервисы, интерфейсы.
  - `04_technology/`: Узлы (серверы), системное ПО, артефакты.
- **`relations/`**: Выделенная директория для хранения файлов связей (Edges) между объектами.
- **`.validators/`**: Скрипты (Linter) для автоматической проверки правил.
- **`.templates/`**: Шаблоны и сниппеты для создания новых элементов.
- **`views/`**: Конфигурации для генерации диаграмм (PlantUML, Mermaid, SVG).

## 3. Спецификация данных (YAML DSL)

### 3.1 Шаблон объекта (Element)

Файл описывает только атрибуты и свойства самого компонента.

```
id: "APP-TRX-001"
name: "Product Orchestrator"
type: "ApplicationComponent" # Тип из ArchiMate 3.2
layer: "Application"
metadata:
  status: "Active"            # Draft, Active, Deprecated
  owner: "v.korobeinikov"
  updated_at: "May 03, 2026"
properties:
  tech_stack: "FastAPI, Python 3.12"
  criticality: "High"
  description: "Оркестрация обработки продуктовых транзакций"
```

### 3.2 Шаблон связи (Relation)

Связи описываются в отдельных файлах для чистоты модели и удобства анализа графа.

```
id: "REL-ORD-001"
source: "APP-TRX-001"
target: "SRV-POSTGRES-01"
type: "Access"                # Тип связи ArchiMate (Serving, Assignment, etc.)
properties:
  protocol: "TCP/IP"
  description: "Хранение данных о транзакциях"
```

## 4. Слой моделирования бизнес-процессов

Для глубокой проработки бизнес-слоя LiteEA интегрирует **LiteEA BPMN Authoring Tool (LiteEA BAT)** — специализированный инструмент для работы с процессами в формате BPMN:

- **Text-first BPMN:** Описание процессов в формате `.bpmn.yaml`, хранящихся в репозитории рядом с элементами архитектуры.
- **Автоматизация:** LiteEA BAT генерирует BPMN 2.0 XML с автоматическим расчетом координат через Layout Engine (ELK.js).
- **Визуализация:** Интерактивное превью в VS Code, интегрированное редактирование и экспорт в SVG/PNG для документации.
- **Интеграция:** LiteEA BAT работает с шаблонами из `.templates/bpmn/` и хранит процессы в `elements/02_business/`.

**Дополнительно:** Полная документация по использованию LiteEA BAT находится в отдельном репозитории `/Users/valerii/Documents/GitHub/LiteEA BAT`.

## 5. Жизненный цикл изменений (Workflow)

Процесс работы с архитектурой аналогичен разработке ПО:

1. **Создание**: Копирование шаблона из `.templates/` в соответствующую папку `elements/`.
2. **Описание**: Редактирование YAML-файла объекта и создание связей в папке `relations/`.
3. **Валидация**: Запуск линтера (`lint.py`) для проверки синтаксиса и логики слоев.
4. **Ревью**: Создание Pull Request. Коллеги проводят аудит изменений через текстовый diff в Git.
5. **Публикация**: Автоматическая генерация диаграмм и обновление архитектурного портала через CI/CD.

## 6. Матрица валидации (Linter Rules)

| Категория       | Описание                                                     |
| --------------- | ------------------------------------------------------------ |
| **Синтаксис**   | Файл должен быть валидным YAML.                              |
| **Атомарность** | Запрещено наличие секции `relations` внутри файлов объектов. |
| **Целостность** | Все `source` и `target` в связях должны указывать на существующие ID объектов. |
| **Семантика**   | Связи должны соответствовать логике слоев ArchiMate 3.2 (например, компонент не может напрямую "обслуживать" бизнес-роль без интерфейса). |
| **Политика**    | Статус 'Active'/'Production' требует обязательного указания владельца в метаданных. |

- **Управление версиями:** Git-диффы четко показывают изменения в контексте каждой организации.

## 8. Матрица способностей с уровнями зрелости (Capability Maturity Model)

**Интеграция от 3 мая 2026:** Извлечено из проекта segments; расширено интеграцией с элементами ArchiMate.

### 8.1 Иерархия способностей (Capability Hierarchy)

Способности организованы по двум осям:

**Вертикальные способности (V)** — основные бизнес-домены:
- V1, V2, V3 — Уровень корня (пример: "Order Management", "Customer Analytics")
- V1.1, V1.2 — Подспособности (пример: "Order Placement", "Order Fulfillment")
- V1.1.1, V1.1.2 — Специфические функции (пример: "Receive Order", "Validate Inventory")

**Горизонтальные способности (H)** — сквозные, поддерживающие способности:
- H1, H2 — Уровень корня (пример: "Data Management", "Security & Compliance")
- H1.1, H1.2 — Подкомпоненты

**Бэклог (V0/H0)** — способности на этапе оценки или отложенные.

### 8.2 Шкала зрелости (5-уровневая CMM)

| Уровень | Название | Описание |
| --- | --- | --- |
| **1** | Начальный (Initial) | Процессы хаотичны, зависят от отдельных людей. |
| **2** | Повторяемый (Repeatable) | Процессы задокументированы, но зависят от исполнителя. |
| **3** | Определённый (Defined) | Процессы стандартизированы, коммуникированы, внедрены. |
| **4** | Управляемый (Managed) | Процессы измеряются, контролируются, статистически управляются. |
| **5** | Оптимизированный (Optimized) | Непрерывное улучшение, автоматизация, извлечение уроков. |

### 8.3 Связь способностей с архитектурой

```yaml
Способность (V1.1):
  ├─ owner_role: ROLE-SALES-001      # BusinessRole элемент
  ├─ business_process: PROC-ORD-001  # BusinessProcess элемент
  └─ applications: [APP-CRM-001]     # ApplicationComponent элементы
```

**Преимущества связи:**
- Единый источник истины: способности связаны с ролями, процессами и системами.
- Трассируемость: видно, какие системы поддерживают каждую способность.
- Управление дорожной картой: планировать как улучшение зрелости способности, так и обновление приложений.

### 8.4 Файл шаблона

Файл `capability-map_template.yaml` содержит примеры иерархических способностей с историческим отслеживанием зрелости и целевыми показателями.

## 9. Расширенные BPMN процессы с дорожками и этапами (Advanced BPMN)

**Интеграция от 3 мая 2026:** Улучшено на основе проекта segments с добавлением системных ссылок и потоков данных.

### 9.1 Когда использовать расширённый BPMN

Используйте `advanced-process-with-lanes.bpmn.yaml` для:
- Сложных, кросс-функциональных процессов.
- Множественных акторов с чёткими областями ответственности.
- Процессов с явными этапами (фазы).
- Качественных контрольных точек и узлов решений.
- Потоков данных между этапами.

### 9.2 Структура дорожек (Lanes)

```yaml
lanes:
  - id: "lane_sales"
    name: "Отдел продаж"
    actor_role: "ROLE-SALES-001"           # Ссылка на BusinessRole
    responsible_system: "APP-CRM-001"      # Ссылка на ApplicationComponent
```

Каждая дорожка представляет организационную роль или актора.

### 9.3 Структура этапов (Stages)

```yaml
stages:
  - stage_id: "S1"
    stage_name: "Инициирование заказа"
    duration_minutes: 30
    steps:
      - id: "S1_receive"
        type: "task"
        label: "Получить заказ"
        lane: "lane_sales"
        supporting_system: "APP-CRM-001"
        required_data: ["CUSTOMER_ID", "ORDER_ITEMS"]
        output_data: ["ORDER_ID"]
        next: "S1_validate"
```

**Отслеживание потока данных:**
- `required_data` — входные данные для шага.
- `output_data` — выходные данные из шага.
- Явные связи между шагами через `next`.

### 9.4 Контрольные точки качества и ветвления

```yaml
- id: "S2_quality"
  type: "serviceTask"
  label: "Проверка качества"
  checks:
    - "Корректные товары"
    - "Правильная упаковка"
    - "Точность этикеток"
  next: "S2_decision"

- id: "S2_decision"
  type: "exclusiveGateway"
  label: "Пакет одобрен?"
  true_path: "S3_start"      # Переход в следующий этап
  false_path: "S2_repack"    # Переупаковка (цикл)
```

**Циклы переработки:** Процесс может вернуться на предыдущий шаг (S2_repack → S2_quality) для исправления.

### 9.5 Ключевые показатели производительности (KPI)

```yaml
kpis:
  - name: "Время от заказа до доставки"
    target: "48 часов"
    calculated_from: ["S1_start", "S3_end"]
```

## 11. Управление архивом (Archive Management)

**Интеграция от 3 мая 2026:** Принцип "никогда не удалять, всегда архивировать".

### 11.1 Принцип

Вместо удаления устаревших или заменённых элементов их перемещают в папку `0.archive/` каждой организации.

```
organizations/acme_corp/
├── elements/
│   └── 02_business/
│       ├── ORDER_MANAGEMENT.yaml    (активный)
│       └── ...
├── 0.archive/
│   └── 02_business/
│       ├── OLD_ORDER_SYSTEM.yaml    (архивный)
│       └── DEPRECATED_PROCESS.yaml
```

### 11.2 Git-конфигурация

Папка `0.archive` исключена из коммитов через `.gitignore`:

```
0.archive/
**/0.archive/
```

### 11.3 Преимущества

- **Историческая запись:** Полная история архитектурных решений остаётся в репозитории.
- **Чистота Git:** Удалённые элементы не засоряют активный код.
- **Восстановление:** Легко вернуть элемент из архива при необходимости.
- **Анализ изменений:** Git diff ясно показывает переход из активного в архив.

## 13. Как начать (Getting Started)

### 13.1 Для новой организации

1. Прочитайте `organizations/NEW_ORGANIZATION_TEMPLATE.md`.
2. Создайте папку `organizations/[your_company]`.
3. Скопируйте структуру из `acme_corp/`.
4. Адаптируйте `.templates/` под ваши элементы.
5. Добавьте первые элементы в `elements/`.

### 13.2 Для моделирования способностей

1. Откройте `organizations/[org]/.templates/capability-map_template.yaml`.
2. Определите вертикальные (V) и горизонтальные (H) способности.
3. Оцените текущий уровень зрелости (1–5).
4. Свяжите способности с ролями, процессами, приложениями.
5. Установите целевую зрелость и дату достижения.

### 13.3 Для моделирования сложных процессов

Рекомендуется использовать **LiteEA BPMN Authoring Tool (LiteEA BAT)** для моделирования и визуализации процессов:

1. Откройте `organizations/[org]/.templates/bpmn/advanced-process-with-lanes.bpmn.yaml` в LiteEA BAT.
2. Используйте графический редактор для определения дорожек (lanes) — участников процесса.
3. Разделите процесс на этапы (stages) с явными фазами.
4. Опишите шаги с указанием потока данных через свойства каждого элемента.
5. Добавьте контрольные точки качества и узлы решений (gateways).
6. Определите KPI для измерения производительности.
7. Экспортируйте визуализацию в SVG/PNG для документации.

**Дополнительная информация:** Полная документация по LiteEA BAT, включая установку, использование и расширенные функции, находится в репозитории https://github.com/LiteEA/LiteEA-BAT или локально в `/Users/valerii/Documents/GitHub/LiteEA BAT`.
