# Recurring Activities in a running process — proposed contract

**Status: proposal, not an implemented or released contract.** For model authors
and implementers of process views and execution-record integrations. Field names,
timing profile and operational policies below remain proposed. These examples
are illustrative data, not execution evidence. No scheduler, runtime store,
validator support or BPMN compiler extension is activated by this document.

An Activity is a process step. An `ACTION` remains bounded transformation work:
Initiative, Programme, Project or Task. This proposal introduces no TYPE prefix
and does not restore the retired project-domain `ACTIVITY` alias.

## Definition, instance and execution

A process definition describes behaviour; an instance starts once and stays
running while its Activities execute repeatedly. One recurring Activity is a
valid process: no second Activity, gateway or artificial loop is required.
Completing an execution does not complete its instance. A separate process
termination condition determines when the instance stops.

| Concern | Current expression | Proposed addition and compatibility |
|---|---|---|

Never duplicate it on the view or reference-only entry. |
| Model lifetime | [CONTRACT.md](CONTRACT.md) §7: `valid_from` / `valid_to`, date precision | Unchanged; these are definition applicability dates, not actual process start/stop. |

### Proposed definition fields

`flow.lifecycle` is optional. If supplied by this profile it is an object with
`mode: persistent` and a required, nonempty `termination_condition`. The latter
is a business predicate described as text, not executable code. Its interpreter
and evidence source must be declared by an implementing integration. A condition
such as “the monitoring mandate has been withdrawn” is independent of whether
this week's review succeeded. Empty or unevaluable conditions are not permission
to stop. A runtime without the predicate capability reports unsupported.

`recurrence` belongs only on Activity kinds (`task`, `userTask`, `serviceTask`),
not on gateways, events, the process root, ACTION or a BPMN view. Within this
profile it requires `flow.lifecycle.mode: persistent`. A promoted STEP resolves
its home PROCESS before this check. The proposed object has two exclusive forms:

| Field | Calendar form | Elapsed form |
|---|---|---|
| `kind` | Required `calendar` | Required `elapsed` |
| `anchor` | Required local date-time, seconds precision, no UTC offset; first candidate occurrence | Required UTC timestamp ending in `Z`; first candidate occurrence |
| `timezone` | Required IANA zone name; never inferred from the machine | Absent; elapsed time is measured in UTC |
| `rule` | Required RRULE string in the restricted profile below | Absent |
| `every_seconds` | Absent | Required positive integer; no months, years or working-day interpretation |
| `ends_before` | Optional UTC timestamp, exclusive upper bound | Same |

The anchor is both the schedule origin and inclusive lower bound. No additional
start field is needed. `ends_before` must be later than the resolved anchor.
Candidate instants are intersected with each instance's actual running window;
starting a second instance creates a separate series with separate execution
identities, never a shared global occurrence. An instance started after the
anchor uses the next eligible instant; pre-start candidates are not missed work.
Exhausting a recurrence window does not terminate a persistent process.

Definitions are pinned by immutable source revision when an instance starts.
Existing instances retain that definition, including its model-validity window;
a later edit does not silently retime or stop them. New instances select a
definition valid on their start date. The existing date-only model lifetime
contract remains unchanged; recurrence bounds and actual timestamps are separate.
An explicit rebind would require a future migration contract.

**Timing recommendation (proposed):** a narrow calendar profile based on
[RRULE in RFC 5545 §3.3.10](https://www.rfc-editor.org/rfc/rfc5545#section-3.3.10),
plus a separate elapsed-seconds form. The calendar and elapsed forms express different timing intents. The proposed first profile accepts exactly `FREQ=WEEKLY;INTERVAL=<positive integer>`;
the local weekday and time come from the anchor. Order is fixed, no whitespace,
duplicate components, COUNT, UNTIL or other components. Reject unsupported forms
rather than interpreting them approximately. Broader calendar frequencies remain
extensions, not silently supported RRULE features.

For this profile, propose skipping nonexistent local times and selecting the
first occurrence of an ambiguous local time; reject an anchor itself in a gap
or fold. These daylight-saving choices need approval along with the timing
profile. Store resolved UTC `scheduled_for` values and the time-zone database
version in the instance record so a later database update cannot rewrite past
occurrences. UTC is an acceptable IANA zone for a calendar rule with no seasonal
clock change. Elapsed candidates are `anchor + n * every_seconds`, for integer
`n >= 0`; completion time never resets the anchor. Calendar weeks can have a
different elapsed length across a clock change; elapsed 604800 seconds always
means that many seconds, even when local wall-clock time changes.

Recurrence says *when eligible*. Actual duration is `finished_at - started_at`;
planned duration is an estimate held separately by the operational integration.
Effort is labour with an explicit unit, potentially from several participants.
Neither duration nor effort is the recurrence interval.

### Proposed runtime records

These are logical interchange records, not new canonical elements, file suffixes
or TYPEs. Their IDs are opaque operational keys. Storage location, retention,
authorization and write APIs must be agreed with the owning runtime before use.
Runtime references to contained steps do not themselves promote a step to canon;
the existing promotion rule still applies to references from model documents.

An instance carries `instance_id`, `process_id`, `definition_revision`, `policy_ref`, `state`,
`started_at` and nullable `stopped_at`; optional `planned_start` / `planned_stop`
are estimates, never substitutes for actual timestamps. States in this proposed
profile are `running`, `stopping`, `stopped`. Calendar instances also record
`timezone_database_version`. Actual timestamps use UTC, seconds precision.
A stopping instance records `stop_requested_at` and `stop_reason`. A stopped
instance additionally needs `stopped_at >= stop_requested_at >= started_at`.

An execution carries `execution_id`, `instance_id`, `step_id`, `scheduled_for`,
`state`, nullable `started_at` / `finished_at`, `outcome` and `evidence` (a list of
operational record references). Proposed execution states are `running`,
`succeeded`, `failed`, `cancelled`. Running records have a start and no finish;
terminal records have both, with start no earlier than scheduled time and finish
no earlier than start. A successful record needs a nonempty outcome and evidence;
a failed or cancelled record needs the reason. An evidence reference alone does
not verify its content or its reader's authorization.

The tuple `(instance_id, step_id, scheduled_for)` identifies one scheduled
occurrence; `execution_id` identifies its execution. The first profile allows
one execution per occurrence, with no implicit retries. Duplicate deliveries
resolve to the same record. A future retry contract must distinguish attempts
without inventing another scheduled occurrence. A record must resolve to a task
in the instance's pinned definition and an eligible instant of that task's rule.

Missed or intentionally skipped occurrences have disposition records keyed by
the same occurrence tuple, with `disposition: missed | skipped`, `recorded_at`
and `reason`; they are not fabricated failed executions. Planned occurrences
and next-due caches likewise cannot be counted as executions. For a nonrecurring
step, an operational execution uses its own activation identity and no scheduled
occurrence tuple; this profile does not redefine existing event-driven execution.

## Operational policy is explicit, never a default

The timing rule cannot decide whether delayed work is still useful or safe.
The following are implementation choices requiring agreement, outside the
recurrence object. The recommendation is an explicit per-instance `policy_ref` binding to
an approved runtime policy; missing or unsupported binding prevents activation.
The illustrative records below assume such a binding, not that one exists today.

| Situation | Proposed explicit policy |
|---|---|
| Missed instant | Skip and record a missed disposition. |
| Previous execution running | No overlap per instance and step; record the skipped occurrence. Different instances remain independent. |
| Pause/resume | Unsupported in the first profile. Reject requests; stopping and starting a new instance is a distinct lifecycle, never called resume. |
| Stop with work in flight | Enter `stopping`, prohibit new starts, drain existing executions, then set `stopped_at`. If work hangs, remain stopping and report it; no implicit timeout or cancellation. |

For the proposed drain policy, a stop request and execution start need one
serialized ordering: if stop wins, no new execution starts; if start wins, that
execution drains. Do not backdate `stopped_at` to the request time. Termination
predicate satisfaction requests stopping; it does not fabricate execution
completion. A zero-in-flight instance can stop immediately. Occurrence identity
and evidence survive stop, and a new start always has a new instance ID.

## One weekly monitoring Activity

Illustrative definition **fragment**; the ordinary PROCESS envelope, admission
and lifecycle fields are required when constructing a full model. This is not a
file accepted by today's validator or evidence of a real weekly job.

```yaml
id: PROCESS-MONITORING-1
flow:
  lifecycle:
    mode: persistent
    termination_condition: "The monitoring mandate has been withdrawn."
  steps:
    - id: STEP-WEEKLY-REVIEW-1
      type: userTask
      name: "Review monitoring observations"
      recurrence:
        kind: calendar
        anchor: "2026-09-07T09:00:00"
        timezone: "Etc/UTC"
        rule: "FREQ=WEEKLY;INTERVAL=1"
  sequence: []
```

The same running instance has two distinct illustrative execution records.
`definition_revision` below denotes a hypothetical immutable model revision,
not a revision of this specification. Evidence URIs are fictional references.

```yaml
instance:

  definition_revision: "example-model-revision-1"

  policy_ref: "example-approved-policy-1"
  planned_start: "2026-09-01T08:00:00Z"
  planned_stop: null
  started_at: "2026-09-01T08:15:00Z"
  stopped_at: null
executions:
  - execution_id: review-a
```

## Multiple Activities and termination

A second illustrative definition fragment has two independently recurring
Activities. No sequence edges are required merely to make the process persistent.
This example adds no implicit “execute the whole flow on each tick” semantics.

```yaml
id: PROCESS-MONITORING-2
flow:
  lifecycle:
    mode: persistent
    termination_condition: "The service retirement is approved and recorded."
  steps:
    - id: STEP-WEEKLY-REVIEW-2
      type: userTask
      name: "Review observations"
      recurrence:
        kind: calendar
        anchor: "2026-09-07T09:00:00"
        timezone: "Etc/UTC"
        rule: "FREQ=WEEKLY;INTERVAL=1"
    - id: STEP-CHECK-1
      type: serviceTask
      name: "Check source availability"
      recurrence:
        kind: elapsed
        anchor: "2026-09-01T00:00:00Z"
        every_seconds: 86400
        ends_before: "2026-10-01T00:00:00Z"
  sequence: []
```

Instance `monitor-b` starts on September 1. The September 7 weekly execution
finishes; `monitor-b` remains running and the daily Activity remains eligible.
Suppose service retirement is approved at September 15 00:01 UTC while that day's
check is running: under the proposed drain policy the instance becomes stopping,
the check finishes at 00:03, and only then does the instance stop. No later review
starts. Without retirement, the daily rule ending on October 1 would not stop
the process or the weekly rule.

This first profile rejects recurrence on a step with incoming or outgoing
sequence edges. Edges among ordinary steps keep their existing meaning. A later
mixed-flow extension must define token enabling, repeated downstream activation
and termination interactions before a renderer or runtime may interpret it.
This restriction avoids a timer bypassing a prerequisite or emitting an
unbounded stream into an ordinary terminating flow.

## Acceptance cases for a future implementation

These are proposed contract cases, not claims about current validation coverage.
No mechanical control is added or changed by this proposal.

| Input or observation | Expected assessment |
|---|---|
| The one-step definition and two records above | Valid proposal example: two occurrences, one running instance. |
| The elapsed rule above | Valid: positive fixed interval, UTC anchor, exclusive end. |
| Two instances with the same step and scheduled instant | Valid distinct occurrences; no cross-instance deduplication. |
| Duplicate delivery of `review-a` | Idempotent readback; no second execution of the same tuple. |
| Calendar with `every_seconds`, elapsed with `rule`, or zero interval | Invalid exclusive-form configuration. |
| Calendar without zone, offset-bearing calendar anchor, or unknown zone | Invalid or ambiguous; no host-zone fallback. |
| `FREQ=DAILY`, cron text, COUNT or duplicate RRULE component | Unsupported profile; do not approximate. |
| End bound equal to/before anchor; occurrence exactly at end | Invalid bound / ineligible occurrence respectively. |
| Anchor in a clock gap or fold | Invalid anchor; future generated gaps/folds use only the agreed policy. |
| Recurrence on a gateway, event, ACTION or sequence-connected task | Unsupported placement; no automatic migration. |
| Reference-only promoted STEP plus a second inline recurrence | Invalid dual definition; resolve the single owning STEP. |
| Execution with nonexistent step, wrong instance, or off-rule timestamp | Invalid reference or occurrence identity. |
| Succeeded execution without start, finish, outcome or evidence | Incomplete; must not count as verified success. |
| Finish before start; execution starts before the instance or after stopping begins | Invalid lifecycle ordering. |
| A running execution at a stop request | Under proposed drain: stopping until execution finishes, no new starts. |
| Rule alone, empty execution list, or missed disposition | No evidence of actual execution. |
| Completing either recurring Activity in the multi-Activity example | Instance remains running unless its termination predicate requests stop. |
| Ordinary PROCESS with no recurrence or lifecycle extension | Preserve existing validation and rendering unchanged. |
| An external timer starts a fresh ordinary process each week | Preserve distinct instance IDs and ordinary completion. It is a different valid trigger pattern, not persistent-instance recurrence. |

## Consumer compatibility

BPMN's supported subset cannot currently express this timing contract. A future
Studio projection may show a recurrence annotation, but must not emit a timer
start event that creates an instance for each occurrence, or an end event after
every recurring completion. Until a faithful mapping is supported, report the
persistent profile as unsupported for executable BPMN export. The existing
SE-001, EE-001 and ACT-001 rules remain unchanged for current BPMN documents.

Existing process-map and process-blueprint references, STEP promotion, and
process-parent composition remain intact. No bulk rewrite of process triggers,
no new ACTIVITY TYPE and no methodology version bump is part of this proposal.
Schema admission and any severity change require their own release compatibility
assessment under [CONTRACT.md](CONTRACT.md) §10; unknown fields accepted by a
permissive parser do not establish supported semantics.

Studio consumers need definition editing, recurrence display, capability checks,
and validator/compiler tests for both persistent and ordinary processes. DSM
consumers need separate definition, instance and execution projections, counts
that distinguish planned/missed/executed work, and durable operational-record
ownership. Neither implementation is delivered here.

Repository MCP readers must distinguish model facts from runtime evidence and
report unsupported execution queries. Runtime joins require a declared source,
identity and scope checks before retrieval; schedules cannot answer “did it run?”.
Any future writes retain the existing [Repository MCP contract](../patterns/transitrix-repository-mcp.md):
base revision, proposed diff, validation, separate review/approval, authoritative
persistence and readback. This proposal creates no new MCP tools or authorization.
